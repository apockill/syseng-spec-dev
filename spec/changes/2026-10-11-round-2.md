## Changes, grouped by the answer that caused them

### Q1: the CLI is how agents edit the spec

- **CLI-1** ✅ modified. "query, check, verify and render" became "query, **edit**, check, verify and render".
- **CLI-5** ✅ added. Before applying an edit, the CLI shows its context: related requirements, verification items, tests, dependents, and approval status.
- **CLI-6** 🟡 added. An edit that touches approved or depended-upon items is applied only after the agent acknowledges each affected item by name. I chose this over a generic "confirm?", which models rubber-stamp.
- **CLI-7** 🟡 added. Edits arrive as one YAML batch on standard input, which avoids shell-quoting failures and saves round trips.
- **CLI-8** 🟡 added. Modifications and removals need a reason.
- **AGENT-20** 🟡 added. A hook blocks direct edits to spec files and names the CLI command to use instead.

### Q4: always mention contradictions, and stop only when it matters

- **AGENT-17** ✅ modified.
  - Was 🟡: "When a requested change contradicts an approved requirement, the agent shall raise the contradiction with the engineer before the change merges."
  - Now: "The agent shall report every contradiction between a request and an approved requirement."
- **AGENT-18** ✅ added. When the contradiction is one you'd likely want to decide before more work happens, the agent stops and asks.

### Q5: reasoning checks run in fresh, non-forked subagents that can read code but not the spec

- **REASON-2** ✅ modified.
  - Was: "…with only its item's prompt and declared inputs in context: no project instructions, memory or conversation history."
  - Now: "…in a fresh subagent that does not inherit the conversation, given only its item's prompt and declared inputs."
- **REASON-5** ✅ added. A reasoning check may read the product's code, but not the spec directory.
- **REASON-6** 🟡 added. A hook in the subagent's own definition enforces REASON-5, because an instruction alone can be ignored.
- **REASON-7** 🟡 added. The subagent skips CLAUDE.md and AGENTS.md. Fresh subagents load those by default.

### Q6: when an accepted failure contradicts a requirement, change the requirement and flag it with alternatives

- **AGENT-19** ✅ added.

### Q7: approvals carry a fingerprint, so the CLI can tell when approved content has changed

- **MODEL-24** ✅ added. Each approval is stored with a fingerprint of what you approved.
- **CHECK-14** ✅ added. Anything without an approval, or whose content no longer matches its approval's fingerprint, is reported as unapproved.
- **MODEL-25** 🟡 added. Approvals apply per item, not per file. You suggested per file; see Q12.
- **MODEL-26** 🟡 added. Each approval stores the approved content, so the review page can show what changed.
- **CHECK-15** 🟡 added. Unapproved items are findings when preparing a merge.
- **AGENT-21** 🟡 added. Only your own actions create approvals, never an agent's tool call. See Q13.
- **REVIEW-8** 🟡 modified.
  - Was: "In a diff, the renderer shall mark each new or changed requirement that an agent proposed."
  - Now: "The renderer shall mark each unapproved item."
- **REVIEW-11** 🟡 modified.
  - Was: "For a spec-first change, the renderer shall show the differences between the approved spec and the final spec."
  - Now: "The renderer shall show each unapproved item's differences from its last approved content."
- **CHANGE-6** removed ("store the spec revision the engineer approved"). MODEL-26 replaces it per item.
- **CHANGE-7** removed ("treat a spec edit as approved once merged"). Approval is now explicit (MODEL-24), so merging no longer implies it.

### Q9: "expensive" includes time, and you can request full runs and walk away

- **NEED-7** ✅ added. Develop quickly, and run full verification occasionally and unsupervised.
- **MODEL-9** ✅ modified.
  - Was: "cheap (fully automated, no model calls) or expensive (needs model calls or subagents)"
  - Now: "cheap, or expensive when it needs model calls, subagents **or a long run time**"
- **MODEL-23** 🟡 added. "Long" means over 60 seconds, and each repository can configure it.
- **VERIFY-6** ✅ modified.
  - Was: "only after the engineer has approved the change for merging"
  - Now: "only when the engineer requests it: for a full run, or when preparing a merge"
- **VERIFY-11** ✅ added. A full run executes every item in every tier, without you present.
- **VERIFY-12** ✅ added. A full run ends with a health summary.
- **VERIFY-13** 🟡 added. The health summary lists status per component, what the run changed and why, unapproved items, and requirements without verification.
- **AGENT-22** ✅ added. During a full run, agents try to fix failures, and their changes stay unapproved. See Q11.
- **REVIEW-13** ✅ added. The review page has approve and feedback controls.

### Your note: persist the context behind decisions
