- **`spec check`**, which enforces:
  - structure: flat elements, one tree, no dependency cycles, unique IDs that are never reused, each item in the right element;
  - traces: every requirement traces up or is marked derived, and every need is served;
  - attributes: rationale and origin;
  - the wording rules;
  - verification-item fields;
  - approval fingerprints;
  - stale views.

  Errors follow the Rust style: each names the rule, says why the rule exists, suggests a fix and links to [docs/rules.md](../../docs/rules.md). Each rule is explained once per run.
- **64 tests**, all passing, and **21 verification items** that link them to the 28 requirements they verify. That includes system-level checks such as SYS-V1 (this repository passes its own checker).

## Agent experience: friction from building this slice

This is AGENT-46 (agents report workarounds) applied to my own work.

1. **There's no `spec edit` yet, so every spec change went through a throwaway Python script.** I also tracked the reason for each change by hand, in this file.
   - Proposal: slice 2's CLI editing, with a reason required for every change (CLI-7, CLI-8), removes both problems.
2. **The `nix develop path:$PWD -c` prefix is needed on every command.** I ran one script outside the shell by mistake, and it failed without PyYAML.
   - Proposal: once you commit `flake.nix`, plain `nix develop` works. An `.envrc` for direnv would make it automatic.
3. **Migrating fingerprints meant reproducing my earlier ad-hoc fingerprint code exactly.** That exposed a bug: NEED-12's old fingerprint had also covered the next heading.
   - Proposal: already done. Fingerprints now live in one module, and approvals go only through `spec approve`.
4. **The rules needed calibrating before they could be trusted.** 18 of 29 first findings were false.
   - Proposal: treat this spec, and each project you later onboard, as a calibration corpus. A new rule ships only after a run against it, with regression tests for its exemptions (as in DR-30).
5. **Mechanical rewording of approved requirements costs you re-approvals even when the meaning is unchanged** (open decision 1).
   - Proposal: the review page should show a word-level diff and allow one-click approval of wording-only changes. Approval itself must stay yours (AGENT-21).
