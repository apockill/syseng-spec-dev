# Node types and their fields

A spec is a tree of **elements**, the parts of the system. Every other node lives in an element. There are seven types of node, each with its own fields:

```
SYS                 element: the root, the whole system
 ├─ NEED-n          needs                  ┐
 ├─ SYS-n           system requirements    │ in the root only
 ├─ SYS-n           constraints            ┘ (numbered with the system requirements)
 ├─ SYS-Vn          verification items
 ├─ STORAGE         element: a part of the system
 │   ├─ STORAGE-n   requirements
 │   └─ STORAGE-Vn  verification items
 └─ DR-n            decision records, filed under the first element they name
```

The type decides where a node may live, what it links to, and which checks apply. An ID shows where a node is filed, not always its type: `SYS-7` may be a system requirement or a constraint, so name the type when you mention one ("SYS-7, a constraint").

Every add goes through `spec edit` as `- add: <type>`; IDs are allocated for you, except an element's. Use block-style YAML throughout, and quote a value that starts with a backtick or contains `: `. `spec schema` prints the tables below, and `spec schema --json` gives them as JSON Schema.

## Writing each type, with examples

**Need.** An outcome the engineer wants, in their terms. A need normally carries intent; one drafted only from documents an agent account wrote carries `basis: derived` and a `why:` instead, until the engineer confirms it.

```
- add: need
  text: The engineer needs to put a new web app online by creating one directory.
  context: Their reasoning and scenarios of use, paraphrased.
  intent: …            # see "Intent records"
  reason: …
```

**System requirement and constraint.** A system requirement says what the whole system shall do and `serves` needs. A constraint limits the solution (a language, a platform, a convention every part follows) and may serve none.

```
- add: system          # or: constraint
  text: Each app shall accept HTTP requests only on a socket in its own directory.
  serves: [NEED-1]
  basis: derived       # or intent: …
  why: the reverse proxy finds apps by their socket.
  reason: …
```

**Requirement.** Refines exactly one requirement of its element's parent (for an element directly under the root, a system requirement or constraint).

```
- add: requirement
  element: STORAGE
  text: The store shall keep each upload until its owner deletes it.
  traces_to: SYS-7
  basis: derived
  why: SYS-7 asks for files to persist.
  reason: …
```

`allow: [{rule: W011, why: …}]` lets a wording rule that doesn't fit this item pass, with the reason on record (references/rules.md). `verification_deferred: <why>` marks a requirement as knowingly unverified for now (no test is possible here, or it waits on hardware); use it sparingly, with a real reason.

**Verification item.**

```
- add: vi
  element: STORAGE
  verifies: [STORAGE-3, STORAGE-4]
  method: test
  technique: unit test
  description: Uploading a file and reading it back after a restart returns the same bytes.
  tests:
    python: [tests/test_store.py::test_upload_survives_restart]   # key: the implementation's name
  reason: …
```

- A verification item for a system requirement or constraint is filed on the root element: `element: SYS` (or whatever the root's ID is).
- A **reasoning check** has no tests; its `description` is the prompt a fresh model answers pass or fail, naming the files or commands it judges.
- A **manual** item says what a person does and observes. It isn't verification until someone has done it.
- A **roll-up** (method `analysis`) verifies a requirement through its children's verification. Use it for a parent whose children fully cover it and where a test of its own would be arbitrary. It's strict: every child must have a verification item, and a deferred child doesn't count (V004). A child may itself be a roll-up, down to verified leaves.
- Describe only what the tests or prompt actually check. "Checks X" when the test checks half of X is the most common audit finding.

**Decision record.**

```
- add: decision
  title: Apps are found by directory, not by a registry
  decided_by: agent
  elements: [SYS]
  requirements: [SYS-7]
  context: What prompted it.
  decision: What was decided.
  alternatives: What else was considered, and why not.
  consequences: What follows from it.
  basis: derived             # or intent: …
  reason: …
```

`decided_by: engineer` only when the engineer made the choice; a decision you recovered from code or commits is `agent` unless they confirm it.

**Element.** `NEED` and `DR` can't name an element (S009).

```
- add: element
  id: STORAGE                # upper case, short; becomes the prefix of its nodes
  title: File storage
  parent: SYS
  depends_on: [AUTH]         # reuse, never a second parent
  purpose: Keeps the files people upload.
  related_code:
    python: [src/store/]
  reason: …
```

## Intent records

Part of any node a person addressed, not a type of its own. `spec edit` fills in `by`, `when` and `fingerprint`.

```
intent:
  basis: stated              # or guided
  context: What was being discussed and what prompted it.
  said: A close third-person summary, never a quote.
  source: human_conversation # the default; or agent_conversation, document, code_comment, commit_message
  source_path: README.md     # required for document, code_comment and commit_message (a file, or a commit hash)
  source_author: Ada <ada@example.com>   # who wrote the source, as `git log` shows it
```

A node no person addressed carries `basis: derived` (something above needs it) or `basis: added` (your own idea), with `why:` saying which. A decision record takes `basis` but no `why`: its context and decision are the reasons.

## Open decisions (`spec decide`)

Questions for the engineer, logged in the open change; not a type of node. See references/review-and-locks.md for a full example.

```
question: …
importance: Why it ranks where it does.
involves: [ITEM-1]           # the nodes it's about
options:
  - label: …
    recommended: true        # exactly one
    detail: …
  - label: …
```

Add `kind: conflict`, and `keeps:` / `rolls_back:` per option, for a conflict with a locked or stated item. Check one with `spec decide --dry-run` before filing it. Until the engineer answers, `--replace D<n>` rewrites it and `--withdraw D<n> --reason "…"` withdraws it. Decision numbers restart in each change, so one of an earlier change is `<change>/D<n>`, such as `round-63/D1`; replacing it files the new decision in the open change (references/review-and-locks.md).

## Settings (`spec/toolkit.yaml`)

Edited by hand; `spec edit` doesn't cover it.
- `implementations`: each with `name`, `root` and one `primary: true`, and `language` where one language covers it. An implementation is a whole working system, which can span languages, frameworks and providers. The `name` is the key under each verification item's `tests`.
- `version_control`: the backend to use, `git` by default.
- `element_order`: the order elements are listed in.
- `flow_down: enforced` makes a requirement that skips a level an error.
